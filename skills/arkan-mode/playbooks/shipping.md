### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Verify each PR independently before it lands.** Use the forge from `playbooks/opening-a-pr.md`, and its **Forge without GraphQL** calls when `gh pr` is blocked. On the broker route, **the forge** in `SKILL.md` names those clients, and step 4 and step 6 name them where they differ. One verifier per PR, a subagent or a separate session that did not write the code, runs the change the way a user would, with the repo's verify skill or the harness's own browser, terminal, or API tools. It compares parent against head and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. The verdict is a PR review bound to the head commit in every repo: the forge note's review call on the direct route, and `agent-gh pr-review <owner/repo> <pr> <head-sha> <body>` on the broker route (**the forge** in `SKILL.md`). Both a repo's `arkan-merge` gate and the broker read that review. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would. The broker marks every agent's verdict, so on a `manual` PR the mark keeps it from counting as the person's `PASS`.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Post the verifier's verdict on the head, then use the merge path recorded in `docs/agents/approvals.md` (`**Merge path:** gate` or `**Merge path:** broker`). With no record, an installed `.github/workflows/arkan-merge.yml` selects the gate. With neither a record nor that file, the person chooses a path in `pre-setup` before shipping. Never call `gh pr merge` or another raw merge api; the chosen path lands it.
   - **gate repository:** the installed `arkan-merge` workflow lands the PR once the head is green and the verdict is on it. A `manual` PR still needs the person's unmarked `PASS` on that head.
   - **broker repository:** a `manual` PR waits for the person's unmarked `PASS` on the head, and every PR waits for green checks. Then run `agent-merge <pr> <head-sha>` with the head pinned while the session is open. Where the owner's broker merge loop is deployed, it merges what the session leaves; never assume the loop runs, and do not treat it as proof. `agent-merge` applies row 6's rule, merges with the head pinned, and asks the forge to delete the branch.

   Land the run's lowest unmerged PR first: a PR whose base is still its parent's branch merges into that branch, not trunk. Read each PR back (state, `mergedAt`, `baseRefName`) until the run's top PR reads merged, because the gate or the broker merges outside the session, and a queued merge is not a landed one. A landed PR reads merged with trunk as its base, not its parent's branch. After a merge lands, retarget the PR whose base was the merged branch to trunk (`gh pr edit <pr> --base <trunk>`; on the broker route, `agent-gh pr-retarget <owner/repo> <pr> <trunk> <head-sha>`), move its patch onto the merge result, and push: with `--force-with-lease` on the direct route, or by merging the new base into the branch on the broker route, whose push is fast-forward only. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Land it once its checks pass and its verdict survives. On the broker route the read-back is `agent-gh pr-view <owner/repo> <pr>` (**the forge** in `SKILL.md`).
5. **Verify the merge cleanup.** A merged PR is not a finished task. The broker removes the merged local worktree and branch when it can, and reports a retained cleanup on stderr while it still exits 0. An `already merged` reply runs no cleanup. After the PR reads merged, check the surviving checkout: `git worktree list` must not list the task worktree, and `git rev-parse --verify refs/heads/<branch>` must fail. If they remain, run `agent-worktree-remove <owner/repo> <worktree-name> <pr> <sha>` with the merged head, or report the retention. The broker requests remote branch deletion but does not verify it; check the remote ref where the route allows it, and report it as unverified otherwise.
6. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Wait on PR events if the harness delivers them; else wait on the current PR's checks: the broker's `agent-gh pr-checks <owner/repo> <pr>` where the broker exists, the repo's own tool otherwise. Re-read the current PR (state, `mergedAt`, `baseRefName`) each time the wait returns, until the ceiling reads merged, with `agent-gh pr-view <owner/repo> <pr>` on the broker route (**the forge** in `SKILL.md`). A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
7. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed, how you confirmed it and its cleanup, and what the next gap needs.
