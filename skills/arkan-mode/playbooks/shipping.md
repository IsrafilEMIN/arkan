### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Verify each PR independently before it lands.** Use the forge from `playbooks/opening-a-pr.md`, and its **Forge without GraphQL** calls when `gh pr` is blocked. One verifier per PR, a subagent or a separate session that did not write the code, runs the change the way a user would, with the repo's verify skill or the harness's own browser, terminal, or API tools. It compares parent against head and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. The verdict is a PR comment posted with `broker pr-comment` (**the forge** in `SKILL.md`). A plain comment is not tied to a commit, so its first line must be `<verdict> at <full-head-sha>`, the sha the verifier ran. A verdict whose sha is not the current head does not describe the PR: step 3 decides whether it still stands. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would. A verdict is evidence for the person, not an approval: the merge decision stays theirs.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time, on the person's go-ahead.** Post the verifier's verdict on the head, then report the PR to the person: its link, head SHA, verdict, and checks. Merging is the person's call, so wait for their go-ahead on that PR. A go-ahead that names the whole run covers each PR in it, as long as each one's checks are green and its verdict survives step 3. Then merge with `broker merge <owner/repo> <pr> <method>` and the repo's merge method, and check that the merge landed on the base branch (a squash merge writes a new sha). If the broker refuses, stop and report its exact error. The person may merge it themselves instead.

   Read each PR back (`gh pr view <pr> --json state,mergedAt,baseRefName`) until the run's top PR reads merged, because a merge queue or the person may merge outside the session, and a queued merge is not a landed one. Every PR targets trunk (no stacks, see **Size** in `playbooks/opening-a-pr.md`), so a landed PR reads merged with trunk as its base. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether a later PR's verdict survives the merge below it. Land it once its checks pass, its verdict survives, and the person's go-ahead covers it.
5. **Verify the merge cleanup.** A merged PR is not a finished task. After the PR reads merged, clean up from a surviving checkout with the cleanup calls in **the forge** in `SKILL.md`, then check: `git worktree list` must not list the task worktree, `git rev-parse --verify refs/heads/<branch>` must fail, and `git ls-remote --heads origin <branch>` must print nothing. Report any of the three that remains.
6. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Wait on PR events if the harness delivers them; else wait on `gh pr checks <pr> --watch`. Re-read the current PR (`gh pr view <pr> --json state,mergedAt,baseRefName`) each time the wait returns, until the ceiling reads merged. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
7. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed, how you confirmed it and its cleanup, and what the next gap needs.
