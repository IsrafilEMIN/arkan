### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Verify each PR independently before it lands.** Use the forge from `playbooks/opening-a-pr.md`, and its **Forge without GraphQL** calls when `gh pr` is blocked. On the broker route, **the forge** in `SKILL.md` names those clients, and step 4 and step 5 name them where they differ. One verifier per PR, a subagent or a separate session that did not write the code, runs the change the way a user would, with the repo's verify skill or the harness's own browser, terminal, or API tools. It compares parent against head and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Where the repo has the `arkan-merge` gate (`.github/workflows/arkan-merge.yml`), the verifier posts the verdict as a PR review on the head commit, with the forge note's review call. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would. On the broker route the verifier posts that verdict with `agent-gh pr-review <owner/repo> <pr> <head-sha> <body>`, a comment review bound to the head commit (**the forge** in `SKILL.md`).
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time — never merge yourself.** Post the verifier's verdict on the head; the repo's merge path lands it: its merge gate where one is installed, the broker (`agent-merge <pr> <sha>`) where none can bind, and the person otherwise. Never call `gh pr merge` or a merge API from the session. Land the run's lowest unmerged PR first: a PR whose base is still its parent's branch merges into that branch, not trunk. Read each PR back (state, `mergedAt`, `baseRefName`) until the run's top PR reads merged, because the gate or the broker merges outside the session, and a queued merge is not a landed one. A landed PR reads merged with trunk as its base, not its parent's branch. After a merge lands, retarget the PR whose base was the merged branch to trunk (`gh pr edit <pr> --base <trunk>`; on the broker route, `agent-gh pr-retarget <owner/repo> <pr> <trunk> <head-sha>`), move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Land it once its checks pass and its verdict survives. On the broker route the read-back is `agent-gh pr-view <owner/repo> <pr>` (**the forge** in `SKILL.md`).
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. Wait on PR events if the harness delivers them; else wait on the current PR's checks: the broker's `agent-gh pr-checks <owner/repo> <pr>` where the broker exists, the repo's own tool otherwise. Re-read the current PR (state, `mergedAt`, `baseRefName`) each time the wait returns, until the ceiling reads merged, with `agent-gh pr-view <owner/repo> <pr>` on the broker route (**the forge** in `SKILL.md`). A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
